# 设计取舍笔记

写这个 skill 之前调研了 [OpenMAIC](https://github.com/THU-MAIC/OpenMAIC)（Open Multi-Agent Interactive Classroom，21K★）与几个成熟 PPT 生成系统。这份笔记记录**抄了什么、为什么不抄什么** —— 免得后来者以为这些决定是随手做的。

---

## 一、从 OpenMAIC 抄的四件事

### 1. 两阶段生成：先大纲，后场景

OpenMAIC 是「大纲 → 场景」两段式。这里保留同样的切分，但**不引入 LLM 编排**：

- A 轨（业务 SOP）负责"讲什么"，产出的是人写的一句话目标与时长表。
- B 轨（技术 SOP）负责"怎么讲"，产出的是场景数据。

**为什么不做全自动生成**：讲解动画的质量瓶颈不在生成速度，而在**判断讲什么**。钩子选哪个数字、边界条件举哪个反例 —— 这是作者的工作。让模型一次生成 90 秒动画，得到的是"看起来像动画的 PPT"：元素都在动，但没有一句话是必须用动画才能说清的。所以这个 skill 定位是**给作者一套能快速表达的工具**，而不是替代作者。

### 2. Action Engine（讲解动作）的抽象

OpenMAIC 的 Action Engine 有 21 种动作（spotlight / laser / …）。这里收了 11 个原子动作，筛选标准是**这个动作是否改变了学习者的注意力或理解**：

- 留下的：`reveal`（出现）、`spotlight`（聚焦）、`draw`（逐笔画出 = 展示构造过程）、`countUp`（数字长大）、`morph`（形变/打字机）、`grow`（图表长出来）、`dim`（降级不重要的）、`flash`（就是这里）。
- 砍掉的：纯装饰性动作（弹跳、旋转、粒子飞入）。它们让页面"活"，但不让理解"发生"，而且会抢注意力。

`draw` 和 `grow` 是这套动作里最有教学价值的两个：**"逐笔画出"和"长出来"直接对应"构造过程"和"量的积累"** —— 这是静态图做不到的事，也是用动画的唯一正当理由。

### 3. 版本化 DSL

场景是纯数据（`deck` 对象），可以 diff、可以 review、可以存进 git。这是 OpenMAIC 用声明式场景定义的核心好处，必须保留。**动画逻辑不该藏在命令式代码里** —— 否则改一个时长要读一遍 JS。

### 4. 离线可导出

OpenMAIC 导出时内联 CDN 依赖。这里走另一条路：**3D 必须有 2D 降级**（`fallback.boxes`），所以离线时降级而不是内联 —— 一个 600KB 的 three.js 内联进单文件 HTML 不划算，而降级路径本来就是作者该写的（G8 门禁强制）。

## 二、故意不抄的四件事

| 不抄 | 理由 |
|---|---|
| Next.js + Postgres + 多模型平台 | 讲解动画不需要服务端。纯静态文件 → 能 git、能内网部署、能离线播、能进 CI |
| 多 agent 协作生成 | 见上：质量瓶颈是判断而非产能。一个作者 + 一个好的校验器 > 五个 agent |
| 富文本/拖拽编辑器 | 编辑器的成本极高，收益是"非程序员也能做"。但这个 skill 的目标用户是能读 JS 的人 —— 他们写 `{at: 1.4, action: 'countUp', to: 20000}` 比拖拽更快更准 |
| 21 种动作全收 | 动作越多，作者越可能用装饰性动作填满时间轴。11 个够表达所有教学意图 |

## 三、自己加的三件事（OpenMAIC 没有的）

### 1. 确定性时间轴（本 skill 的核心发明）

`render(t)` 纯函数。OpenMAIC 的动作引擎是**运行时事件流**（`play()` 之后按时间触发），这带来三个问题：不能可靠 scrub、不能截图断言、导出视频会闪。

改成纯函数后，验证器可以做**双渲染逐字节 diff** —— 这是"确定性"从口号变成可执行断言的关键。代价是：作者不能写"上一步的累积结果"这类有状态动画，必须把状态表达成 `t` 的函数。这个代价值得付，而且通常逼出更清晰的动画设计。

### 2. 门禁而非 checklist

`authoring-gates.md` 里的每一条都是**可执行断言**，不是"请注意……"。

特别是 **G3（每一幕都在动）**：它专门检测"静态 PPT 冒充动画"—— 同一个 `t` 早/晚截图必须不同。这条门禁的存在，本身就是对这个 skill 定位的声明。

### 3. 3D 与 2D 共用一条时间表

`templates/scenes.instancing.js` 里的 `submissionAt(t)` 是唯一的动画语义，three 路径与 2D 降级路径都从它取状态。

这是从 D3 失败模式（"3D 场景与 2D 讲的是两件事"）反推出来的设计。常见错误是两个后端各写一套动画，降级后讲的完全是另一个故事。**抽一条共享时间表**是唯一正确的解法，而且它顺便让 3D 代码变简单（3D 只管"怎么画"，不管"什么时候画什么"）。

### 4. `below`：承认"声明的盒 ≠ 画出来的内容"

用户第二次提"遮挡问题很多时候"的时候，我不该再去修某一页 ——
**同一个症状反复出现，说明它不是 bug，是方法。**

量了一遍（CDP 探针逐秒取所有 `[data-el]` 的绘制矩形、两两求交），根因是：

```
m1/m2/m3  声明 h:11%  =  79px
          实际内容    = 110px      （scrollHeight 110 > clientHeight 79）
          overflow    = visible
```

字画到盒外 31px，压住下一排。而当时的 `G2b` **只查 4 个文字类、且只看
`firstElementChild`** —— 所以完全看不见 metric 溢出。

结论：**DSL 逼作者手填 `h`，而这个值在渲染前根本不可知。**
补一个门禁只能事后报警，作者还是得手算。真正的修法是**换掉这个契约**：

```js
{ id: 'm', type: 'metric', ..., x: 6, w: 19, decimals: 2, below: 't', gap: 3 }
```

有 `below` 就不填 `y`；引擎渲染完量**实际高度**，再累加位置。
配套两条门禁：`G2b` 扩到全类型 + 查元素自身盒；新增 `G14` 两两不相交。

**踩到的第二个坑（值得单独记）：** `below` 第一版实现给没 `y` 的元素设了
`style.top = "undefined%"` —— 这是**无效 CSS**，浏览器忽略它，元素退回文档流堆在顶部。
于是 `below` 解析时量到的是"测量那一刻"的临时布局，**同一个 deck 在不同时机
建场景会得到不同位置**（我的探针 y587，门禁里 y771，差 190px）。
改成"量高度、累加 top"（位置无关）之后才确定。

一个门禁和一个原语，两次都是**先量、再改契约**，而不是先改代码。

## 四、已知边界

- **不做音频轨合成**：TTS 走浏览器 `speechSynthesis`（`?narrate=1`），只在现场讲课时有用；导出视频是无声的（可后期配音，字幕帧已经烘焙进画面）。
- **不做转场特效**：幕与幕之间是硬切。转场会掩盖内容，且让"确定性截图"变复杂。
- **`three` 只做静态场景 + 逐帧状态更新**：不做物理、不做骨骼动画。要那些的话，`update(t, el, api)` 里自己接物理引擎，但必须保证 `t → 状态` 是纯函数。
- **验证器需要 Chrome**：截图比较依赖真实浏览器。CI 里没有 Chrome 时只能跑 `lint-scenes.mjs`（静态部分）。
- **中文语速 4.6 字/秒是硬编码**：讲给不同听众需要调。它定义在 `engine/scene.js` 的 `SPEAK_CPS`。
